# Step 11.1 to 11.2 Handoff

## Completed boundary

Step 11.1 reassessed and documented the frontend architecture without creating
the frontend. The accepted design keeps one isolated Next.js 16 App Router
package below `frontend/`, defaults routing and data reads to Server Components
and limits Client Components to small interactive islands.

The package boundary fixes Node.js 24.21.0 LTS, npm 11.19.0, an exact committed
lockfile and strict TypeScript options. The generated-client design uses a
canonical local FastAPI OpenAPI snapshot, pinned `openapi-typescript` output and
a pinned `openapi-fetch` runtime behind one server-only transport adapter. No
client has been generated yet.

Backend responses remain uncached. URL search parameters own filters and
offset pagination, request IDs remain end-to-end correlation values and the
uniform backend error envelope maps to one safe frontend error type. Loading,
empty, not-found, unavailable, rate-limited, no-active-model and free-tier
cold-start states are all explicit product states.

Native CSS, CSS Modules and custom-property tokens form the styling boundary.
No UI system or charting dependency has been selected. WCAG 2.2 AA, responsive
semantic tables and Chromium/Firefox/WebKit coverage are required by the later
frontend test step.

## Contract facts carried into Step 11.2

- The FastAPI document is OpenAPI 3.1 with exactly sixteen GET operations.
- Collection responses use `items` plus `page`; limit defaults to 50 and is
  bounded at 100.
- Every response has `X-Request-ID`; ordinary errors use the version-one
  envelope, while readiness retains its typed 503 health body.
- Production readiness intentionally reports PostgreSQL `ready` and active
  model `no_active_model` with aggregate HTTP 503.
- The actual registry state is `development_accepted`; it is not active.
- Production prediction and simulation collections are empty.
- The backend emits `Cache-Control: no-store` and its CORS allowlist is empty.
- The browser must not contact Render directly; the frontend uses the
  server-only `PLP_API_BASE_URL` origin.
- No API operation exposes players or squads. Step 11.5 must retain an explicit
  unavailable state unless separately authorized backend work changes the
  contract.
- No production current-data provider is selected or connected. The later
  match centre is a manual refresh of persisted state, not a live-feed claim.
